## 1. 目的

#22（技術基盤: Go + 組み込みTUI）と #24（競合・エコシステム調査）の結果を集約し、`lead` の提供形態と基本UXモデルを正式に確定する。後続の #25（ワークフロー柔軟性）、#26（配布設計）の前提となるコア方針を定める。

---

## 2. 提供形態の決定

### 2.1 結論: スタンドアロン単体CLIバイナリ `lead`

`lead` は **Go 製の単一静的バイナリとしてスタンドアロン配布する**。`gh extension` は**採用しない**。

### 2.2 `gh extension` を採用しない理由

#24 の調査では `gh extension` の配布メリット（1コマンドインストール、認証透過）が指摘された。リポジトリ名や起動コマンド名は本質的な論点ではない。採用否判断に関わるのは以下の構造的な理由である。

1. **`lead` の責務は GitHub 操作ではない**: `lead` は Issue 選定・エージェント起動・マルチペイン構成・CI 監視をオーケストレートするツールであり、`gh` はその中の 1 アダプタに過ぎない。GitHub 操作専用の拡張点である `gh extension` は、責務の位置づけと合致しない。
2. **配布・リリースサイクルの独立性**: `gh extension` 経由の配布は `gh` エコシステムの慣行（リポジトリ構成・リリース形式）に従うことになる。スタンドアロンバイナリ + GitHub Releases / Homebrew であれば、リリース方針・バージョニングを `lead` 側で独立に制御できる。
3. **`gh` 非依存の実行パスの確保**: Herdr 連携やエージェント起動は `gh` なしでも成立する機能であり、`gh` が前提となる配布形態に縛られる理由がない。
4. **後付けは容易**: スタンドアロン配布を主としつつ、需要が生じた時点で `gh extension` 用の薄いラッパーを追加することは低コストで可能。逆に extension 前提で始めると剥がすのが難しい。

### 2.3 配布方式（方針レベル・詳細は #26）

- **GitHub Releases**: goreleaser 等によるクロスコンパイル済みバイナリの公開。
- **Homebrew**: tap 経由のインストール。
- **インストールスクリプト**: `curl | sh` 形式の簡易導入。

### 2.4 Herdr 環境自動検出（維持）

スタンドアロンでありながら、実行環境を自動検出して動作を変える。

- `HERDR_ENV=1` かつ `herdr` コマンドが存在する場合: `herdr pane split` / `herdr pane send-text` で左右マルチペインを構成。
- 非検出時: インラインフォールバック（単一端末で動作）。

## 3. 基本UXモデルの決定

### 3.1 1ストローク選定（組み込みTUI）

- Issue 一覧のあいまい検索・プレビュー・エージェント同時選択を、`koki-develop/go-fzf`（bubbletea ベース）による**組み込みTUI**で実現する。外部 `fzf` コマンドには依存しない。
- キーバインド（`--expect` 相当）で Issue 選択とエージェント決定を同時に行う（例: `[Enter]`=agy, `[Ctrl-D]`=devin, `[Ctrl-O]`=opencode）。

### 3.2 Human-in-the-loop レビュー

- 生成したプロンプトをエージェントに**自動送信しない**。右ペインの入力欄に事前展開し、ユーザーが確認・編集して `[Enter]` で発火する待機状態を作る。

### 3.3 左右マルチペイン

- **左ペイン（人間の司令塔）**: `lead` 実行、`git status` / `git diff` 監視、手動テスト検証、`ci-wait` による CI 監視。
- **右ペイン（エージェント作業場）**: エージェント起動・作業ログ・承認要求の表示。

---

## 4. 後続タスクへの基本要件

### 4.1 #25（ワークフロー柔軟性）

- Issue と PR の対応関係（1:1 を基本としつつ、複数PR分割等の拡張余地）を設計すること。
- Issue ライフサイクル（着手〜マージ〜クローズ確認）の状態管理を定義すること。
- 自動マージの可否を Issue 単位・ユーザー設定で制御できること（調査タスク等は自動マージしない運用に対応）。

### 4.2 #26（配布方式）

- 2.3 の3経路（GitHub Releases / Homebrew / インストールスクリプト）の具体設計を行うこと。
- スタンドアロン配布を主とするため、`gh extension` 用のエントリポイント・リポジトリ構成は設計対象に含めない。
- バイナリ名は `lead` で統一すること。

---

## 5. 決定事項まとめ

| 項目 | 決定 |
| :--- | :--- |
| 提供形態 | スタンドアロン単体CLIバイナリ `lead`（Go 製） |
| `gh extension` | **採用しない** |
| 配布 | GitHub Releases / Homebrew / インストールスクリプト（#26 で詳細設計） |
| Herdr 連携 | 環境自動検出によるマルチペイン、非検出時はインラインフォールバック |
| 選定 UX | 1ストローク選定（`go-fzf` 組み込みTUI） |
| レビュー UX | Human-in-the-loop（プロンプト事前展開待機） |
| 画面構成 | 左右マルチペイン（左: 人間 / 右: エージェント） |

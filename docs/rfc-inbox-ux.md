# RFC: 受信箱（Inbox）UX — 人間のゲートを Issue 承認に一本化する

- **Issue**: [#90](https://github.com/kuwa72/lead-cli/issues/90)（子: #91 受信箱 / #93 ディスパッチャ / #94 仕様 AI / #92 マージ後確認ループ）
- **Supersedes**: [rfc-16-product-ux.md](rfc-16-product-ux.md) §3（基本UXモデル）
- **前提として維持**: [rfc-25-workflow-flexibility.md](rfc-25-workflow-flexibility.md)（モード・状態モデル・finish）、[AGENTS.md](../AGENTS.md)（TDD・PR・マージ手順）
- **ステータス**: Proposal
- **更新日**: 2026-09-08

## 1. 結論

| 項目 | 決定 |
|---|---|
| 人間のゲート | **Issue の承認（`needs-review` → `ready`）のみ**。プロンプト確認・コードレビューはゲートにしない |
| 人間の常設画面 | エージェントの作業画面ではなく **受信箱**（人間にしかできない仕事の一覧） |
| エージェントの実行形態 | **ヘッドレス・並列・worktree 分離**。人間は覗きたいときだけフルスクリーンで乗り込む |
| 実装 AI の完結範囲 | 単一セッションで TDD → PR → CI 待ち → squash merge → Issue close まで |
| 人間の実機確認 | マージ後の `main`（＝ステージング）で**非同期**に行う。ゲートではない |
| 情報の置き場 | GitHub Issue スレッドを唯一の正とする。`lead` は隠し状態を持たない |
| 画面分割・herdr | 中核 UX から外す。herdr はタブ提供の任意依存 |

## 2. 解決する問題

RFC-16 は「人間が右ペインでプロンプトを確認して Enter」「左ペインで diff を監視」を中核に置いた。これは人間がコードを見る前提の UX である。実際の運用前提は次のとおりで、噛み合わない。

- 仕様を考えて Issue を起票するのも、コードを書いてマージするのも AI
- 人間は Issue のレビュー・整形、詰まったときの一言、方向修正、マージ後の実機確認だけを行う
- 人間はコードレビューをしない
- Issue は直列で処理されることが多く、常時 Issue 一覧を表示しておく意味がない
- 画面分割が常に残るのは邪魔で、人間がエージェントを見続ける必要もない

## 3. 役者と場所

| 役者 | 実行場所 | 仕事 |
|---|---|---|
| 人間 | 受信箱（1画面）＋ステージング実機 | 承認・編集・却下・一言・実機確認・規約編集 |
| 仕様 AI | ヘッドレス（RFC-25 `research` モード相当） | 人間の一言と AGENTS.md から、受入条件付き Issue を「AI が 1 セッションで走れる粒度」で起票し `needs-review` を付ける |
| 実装 AI（並列 N 本） | worktree、ヘッドレス | `ready` な Issue を 1 件担当し、AGENTS.md の手順で TDD → PR → `ci-wait` → merge → close。失敗が続けば `blocked` |
| ディスパッチャ | 受信箱プロセス内の前景ループ（design.md §7 の server 実装を流用） | `ready` 監視・worktree 払い出し・並列上限・受信箱への集約 |

| 場所 | 役割 |
|---|---|
| GitHub Issue / PR / CI | 状態の正。人間の一言も AI の報告もすべて Issue コメント |
| `main` ブランチ | ステージング。人間の実機確認対象 |
| worktree（Issue ごと） | 実装 AI の作業場。完了後に削除 |
| `$XDG_STATE_HOME/lead/workflows.json` | Issue ↔ worktree ↔ pane ↔ 実行中プロセスの対応表。GitHub にない情報だけを持つ |
| プロジェクト内 `AGENTS.md` | 全体の方向修正の唯一の入口。`lead init` が管理ブロックを配る |

## 4. ループ

```
人間 ──say "一言"──▶ 仕様AI ──起票(needs-review)──▶ 受信箱
                                                     │ 人間: a/e/t/x
                                                     ▼ ready
                                              ディスパッチャ
                                                     │ worktree + ヘッドレス起動
                                                     ▼
                                              実装AI: TDD→PR→CI→merge→close
                                                     │
                     ┌──────── blocked ──────────────┤
                     ▼                               ▼
                受信箱「止まってる」            main（ステージング）
                人間: t で一言 → 再走            人間: 非同期に実機確認
                                                     │ NG なら
                                                     └──▶ say "一言" へ戻る
```

同期が必要なのは「承認」と「止まってるへの一言」の 2 点だけ。実機確認と方向修正は完全に非同期で、未確認が溜まっても AI は止まらない。

## 5. 受信箱

### 5.1 画面

```
lead — kuwa72/lead-cli                        実行中 3 / 並列上限 3   ⟳ 12s前
──────────────────────────────────────────────────────────────────────────────
レビュー待ち (2)
  > #92  fix(order): 在庫0で発注ボタン押下時に警告        仕様AI  3分前
    #93  feat(inbox): needs-review→ready 遷移の実装        仕様AI  8分前
止まってる (1)
    #88  CI失敗 ×3  test_finish_merge が flaky            claude  25分前
最近マージ (5)  ▸
実行中 (3)      ▸
──────────────────────────────────────────────────────────────────────────────
a 承認  e 編集して承認  x 却下  t 一言返す  p 覗く  n 実機NG  r 規約  s say  ?
```

- 区画は「人間にしかできないこと」の順。上 2 区画が空なら人間の仕事はない
- 「最近マージ」は前回確認以降にマージされた Issue の一覧。実機確認のための参照であり、操作を要求しない
- 「実行中」は既定で畳む。見る必要がないから

### 5.2 キー

| キー | 動作 | GitHub への反映 |
|---|---|---|
| `Enter` | 本文をフルスクリーン表示（受入条件・コメント含む） | なし |
| `a` | 承認 | `needs-review` を外し `ready` を付ける |
| `e` | `$EDITOR` で本文を編集して承認 | 本文更新 + `ready` |
| `x` | 却下 | close（理由は任意の一言） |
| `t` | 一言返す | Issue コメント。仕様 AI（レビュー待ち）または実装 AI（止まってる）が再走 |
| `p` | 覗く | 実行中 / 止まってるエージェントの画面にフルスクリーンで乗り込む。`q` で戻る |
| `n` | 実機 NG | 一言を入力 → 仕様 AI が元 Issue にリンクした追い Issue を起票 |
| `r` | 規約 | `AGENTS.md` を `$EDITOR` で開く |
| `s` | say | 一言を入力 → 仕様 AI が起票 |
| `o` | ブラウザで開く | なし |

分割ペインは作らない。`p` は herdr があれば新タブ、なければカレント端末を明け渡す（tmux attach 相当）。左右配置の問題は消える。

## 6. コマンド

```text
lead [--parallel N]        # 受信箱（既定サブコマンド）。開いている間ディスパッチャが前景で動く
lead say "<一言>"          # 仕様 AI に起票させる（受信箱外からの最短入力）
lead run <issue> [flags]   # 手動ディスパッチ（`ready` を経ないオーバーライド）
lead peek <issue>          # `p` と同じ
lead init / doctor / setup / update / completion   # 現行どおり
lead status / finish / clean                       # 現行どおり（RFC-25）
```

`lead work` は `lead run` に改名し、人間の通常フローからは外す。

## 7. ディスパッチャ

- 受信箱が開いている間だけ動く。`ready` ラベルの open Issue を定期ポーリング
- 並列上限 N（既定 2）。空きがあれば古い順に 1 件取り、worktree を払い出し、`agents.impl` で指定された実装 AI をヘッドレスモードで起動
- 受信箱を閉じても起動済みのエージェントは殺さない。再度開いたとき `workflows.json` から実行中を再接続する
- 起動プロンプト = Issue 番号・タイトル・本文・受入条件 ＋ AGENTS.md の管理ブロック ＋ 完了定義（PR merge・Issue close まで）
- 各エージェント CLI のヘッドレス／自走フラグへのマッピング層を持つ（#83）。**フラグは実機の `--help` で確認し推測で組み立てない**（AGENTS.md テスト品質ルール 2）
- 完了（Issue closed）で worktree を削除し `workflows.json` から除く
- 失敗規約: CI 失敗またはエージェント異常終了が 3 回で `blocked` ラベル＋原因コメントを Issue に書いて停止。人間の `t` で再走
- ガードレール保護: PR の変更ファイルに `AGENTS.md`・`.github/`・CI 定義・`.claude/`・`.devin/` が含まれる場合、マージポリシーを `confirm` に落とし受信箱「止まってる」に出す（AI が自分の規約を書き換えない）

## 8. 仕様 AI

- 入力: 人間の一言、リポジトリの AGENTS.md、（`n` の場合）元 Issue
- 出力: `gh issue create` で 1〜数件。タイトルは `internal/prompter.LintTitle` 規則、本文は Mode / Purpose / Scope / Acceptance criteria / TDD first step（`prompter.Render` の分解テンプレートを流用）
- ラベル: `needs-review`。親子がある場合は本文で相互参照
- `t` で一言が付いたら、その Issue を再起案（本文を編集、コメントで差分を説明）
- GitHub 以外に状態を持たない

## 9. 安全装置（人間がコードを見ない代わりに）

| 装置 | 実現 |
|---|---|
| CI 必須・ブランチ保護 | `lead doctor` で検査し、未設定なら受信箱はディスパッチを開始しない（#67） |
| 受入条件の追跡 | 実装 AI は受入条件を PR 本文にチェックリスト転記。「最近マージ」の詳細でそれを表示 |
| 規約ファイル保護 | §7 のガードレール保護 |
| 暴走の上限 | 並列上限・失敗 3 回停止・1 Issue 1 セッション（AGENTS.md セッション管理ルール） |
| 監査 | すべて Issue コメントに残る。`lead` のログは補助 |

## 10. 捨てるもの・残すもの

| 捨てる | 理由 |
|---|---|
| Human-in-the-loop のプロンプト確認 Enter（RFC-16 §3.2） | ゲートは Issue 承認へ移った |
| 左右マルチペイン（RFC-16 §3.3）、herdr 必須 | 覗くときだけフルスクリーン。herdr は任意 |
| Issue picker を主画面にする（RFC-16 §3.1） | 受信箱の一区画に降格 |
| `/lead-flow` スキル（エージェントが `lead work` を呼ぶ入口） | エージェントは起動される側。循環を解消 |
| `lead work` を人間が打つ | `lead run` に改名し手動オーバーライドへ |
| 「1 ストローク選定」のエージェント同時決定キー | エージェント選択はディスパッチャ設定。人間が毎回選ばない |

| 残す | 位置づけ |
|---|---|
| AGENTS.md の Issue 開発フロー・TDD・セッション規約 | 実装 AI の行動規範。変更なし |
| RFC-25 のモード・状態モデル・`finish` | 実装 AI の完了処理として使う |
| `internal/finish`（ci-wait・merge・close） | そのまま |
| worktree（#40/#72）、`resume`（#74） | 並列実行と再走の基盤 |
| `internal/prompter` | 仕様 AI の中身 |
| design.md §7 の server / socket API | ディスパッチャの土台 |
| `lead init`（AGENTS.md 管理ブロック） | 配る中身を「実装 AI 向け完了定義」に更新 |

## 12. 実装時の検証要件

AGENTS.md テスト品質ルールに従う。

- 受信箱: ダミー `gh` が返す Issue 一覧・ラベルから区画分けが正しいこと、各キーが `gh` に渡す引数（ラベル付け外し・コメント本文・close）を厳密に検証
- ディスパッチャ: ダミー `gh`・ダミーエージェントで「`ready` 取得 → worktree 作成 → 起動引数 → 完了で削除」「失敗 3 回で `blocked`」「ガードレール対象ファイルで `confirm` 化」を一時 HOME・一時リポジトリで検証
- 仕様 AI: 起票時の `gh issue create` 引数（タイトル規則・ラベル・親子参照）を golden で検証
- 実機: 対象エージェント CLI のヘッドレスフラグは PTY スモークテストで確認

## 13. 決定済みの補足（2026-09-08）

| 項目 | 決定 |
|---|---|
| ディスパッチャの起動形態 | **受信箱を開いている間だけ動く前景ループ**。人間は受信箱を開きっぱなしにする運用。常駐 `daemon` は作らない（design.md §7.2 と整合）。§6 の `lead daemon` は削除し、`lead --parallel N` の受信箱オプションにする |
| 仕様 AI と実装 AI のエージェント | **分けられるようにする**。設定 `agents.spec` / `agents.impl`（既定は同じ値）。ディスパッチャは役割ごとに参照する |
| ラベル名 | `needs-review` / `ready` / `blocked` で**固定**。設定化は必要になってから |

### 13.1 Issue の区画分け（フォルダ表示）の手段

受信箱は次の 3 層で Issue を分ける。

| 層 | 手段 | 用途 |
|---|---|---|
| 区画 | **ラベル**（`needs-review` / `ready` / `blocked`） | 人間の作業状態。`gh issue list --json labels` 1 回で取得できる。1 Issue に状態ラベルは 1 個、差し替えは `lead` が行う |
| 区画内の入れ子 | **Sub-issues（GitHub 親子）**。当面は本文の相互参照で代替 | RFC-25 `split` の親を畳み、子を下げて表示。GraphQL 経由のため後から足す |
| 進行区画 | **ローカル導出**（open PR の有無・CI 状態・`workflows.json`） | 「実行中」「最近マージ」。ラベルにしない（AI の付け忘れで受信箱が嘘をつかないため） |

Milestone・Issue Type・Projects v2 は採用しない。Projects v2 は GitHub UI 側でも同じ列を見たくなったときに、ラベル → 列の自動化ルールを貼るだけで両立できる。
